**작성일**: 2026-11-25
**버전**: v0.1
**설명**: 방법론 §2.3 아키텍처 결정 기록(Decision Records)의 등록부. 결정 목록, 상태, 재검토 조건, 정본 위치를 모은다. 각 결정의 배경·대안·근거 원문은 시스템 구조 설계서 v1.10 7장이 정본이므로 여기서는 복사하지 않는다.

## 1. 목적과 쓰는 법

- 결정이 몇 개 있고 각각 어디에 적혀 있는지, 지금도 유효한지를 한눈에 보게 한다.
- 새 결정은 정본(시스템 구조 설계서 7장)에 `ADR-NN`으로 추가하고, 이 등록부에 한 줄을 더한다.
- 결정을 바꿀 때는 이전 결정을 지우지 않고 상태를 `대체됨`으로 바꾼 뒤 새 번호를 쓴다.

## 3. 결정 간 관계

- ADR-02(외부 API 없음)는 ADR-03(오프라인 동작 전제)과 ADR-04(설치 없는 exe)를 받쳐 준다.
- ADR-07(순수 domain)은 ADR-08의 규칙을 테스트하기 쉽게 만든다.
- ADR-01의 재검토 조건(GPL)은 배포 계획과 연결되어 있다. 배포 계획은 형상·배포관리 정의서 4.1절에서 확인 필요로 남아 있다.

## 4. 열린 결정 (아직 ADR이 없는 항목)

| 후보 | 배경 | 상태 |
|---|---|---|
| 배포 전달 경로 | 학생에게 exe를 어떻게 전달할지 | 형상·배포관리 정의서 8절에서 확인 필요 |
| 릴리스 버전 체계 | Git 태그와 버전 번호 규칙 | 형상·배포관리 정의서 4.2절에서 확인 필요 |
| 자동 백업 보관 개수 | 개수 제한 정책의 근거 | 확인 필요 (구현 일지 M7에 "최근 3개 유지" 계획 기록) |

열린 결정이 확정되면 `ADR-09` 이후로 정본에 추가하고, 이 표에서 뺀다.

## 5. 새 결정 기록 양식

시스템 구조 설계서 7장에 아래 형식으로 쓴다.

- **배경**: 왜 결정이 필요한지
- **대안**: 검토한 선택지와 단점
- **결정 근거**: 고른 이유와 감수한 단점
- **재검토 조건**: 언제 다시 볼지
