## 1. 개요

### 1.1 목적
- 요구사항(FR/NFR)을 모듈·클래스·함수 단위로 배치한다.
- 순수 로직(간격 반복, 퀴즈 구성)을 UI와 DB에서 분리해 단위 테스트가 가능하게 한다.
- 구현 순서와 테스트 기준을 정한다.

### 1.2 확정된 기술 결정

| 항목 | 결정 | 근거 (ADR 7장) |
|------|------|---------------|
| 언어 | Python 3.11+ | 기획서 |
| GUI | **PyQt6** | 현행 Qt 6 세대, 신규 프로젝트 |
| 예문 출처 | **없음 (외부 API 제거)**: CSV 기본 예문 + 학생 입력 예문 | 키·인터넷 불필요, 오프라인 동작 (ADR-02) |
| DB | SQLite + SQLAlchemy 2.x | 기획서, 데이터 설계서 |
| DB 저장 위치 | 배포: `%APPDATA%\SmartVoca\` / 개발: 프로젝트 `data/` | 쓰기 권한과 재설치 안정성 |
| 대상 OS | Windows 우선, macOS는 후속 | 개발 환경과 빌드 환경 |
| 로그 | 필수 포함 (표준 `logging`) | DB·백업 오류 추적 |
| 접근성 글꼴 조절 | 1차 버전 제외 | 레이아웃 재검토 비용 |
| 테스트 | `pytest` (UI는 수동 + 선택적 `pytest-qt`) | 기획서 12장 |
| 패키징 | PyInstaller (`--onefile --windowed`) | 기획서 10장 |

## 2. 아키텍처

### 2.1 계층 구조

```
┌──────────────────────────────────────────────┐
│ UI (PyQt6)                 src/ui/           │  화면 표시, 사용자 입력
├──────────────────────────────────────────────┤
│ Service                    src/services/     │  유스케이스 조율, 트랜잭션
├──────────────────────────────────────────────┤
│ Domain (순수 로직)          src/domain/       │  간격 반복, 퀴즈 구성, 보기 선정
├──────────────────────────────────────────────┤
│ Data Access                src/models.py     │  ORM 모델, 세션 관리
│                            src/database.py   │
├──────────────────────────────────────────────┤
│ SQLite (smart_voca.db)                       │
└──────────────────────────────────────────────┘

외부 연동 없음 (오프라인 동작, ADR-02)
```

### 2.2 계층 규칙

1. **UI는 DB에 직접 접근하지 않는다.** UI는 Service만 호출한다.
2. **Domain은 PyQt, SQLAlchemy를 import하지 않는다.** 입력은 리스트·딕셔너리, 출력은 리스트·값이다. 그래서 단위 테스트가 DB 없이 돈다.
3. **Service가 트랜잭션 경계다.** 한 문항 답변의 Quiz 기록과 Progress 갱신은 하나의 Service 메서드 안에서 함께 커밋한다 (데이터 설계서 7.3).
4. **외부 API를 두지 않는다.** 예문은 CSV 기본 예문과 학생 입력으로만 제공한다 (ADR-02). 앱은 인터넷 없이 동작한다.
5. **오래 걸리는 작업은 UI 스레드에서 실행하지 않는다.** 현재 설계에서 그런 작업은 없다 (6장). 작업이 길어지면 `QThread` 워커를 쓴다.

### 2.3 주요 실행 흐름 개요

```
main.py
  → 로거 설정 → 경로 결정 (config) → DB 준비 (없으면 db_init) → 무결성 확인
  → MainWindow 생성 → 사이드바 메뉴 구성 → 홈 통계 로드
  → 종료 시그널 → backup_service.auto_backup() → 세션 저장 확인
```

## 4. 모듈 상세

### 4.1 규칙 상수 (`src/domain/rules.py`)

| 상수 | 값 | 출처 |
|------|-----|------|
| `WRONG_RATE_THRESHOLD` | 60 | FR-3.1, FR-3.4 자주 틀린 기준 |
| `STALE_DAYS` | 7 | FR-3.1, FR-3.4 마지막 복습 경과일 |
| `MASTERED_STREAK` | 5 | FR-4.0 숙달 기준 |
| `REVIEW_INTERVALS` | `{1: 1, 2: 3, 3: 7, 4: 14, 5: 30}` | FR-4.0 연속 정답별 간격 (5 이상은 30) |
| `WRONG_INTERVAL_DAYS` | 1 | FR-4.0 오답 시 간격 |
| `RATIO_WRONG` | 0.10 | FR-3.1-A 자주 틀린 단어 기본 비율 |
| `RATIO_REVIEW` | 0.20 | FR-3.1-A 복습 대상 기본 비율 |
| `BONUS_MAX` | 5 | FR-3.4 보너스 최대 개수 |
| `MIN_OPTION_WORDS` | 4 | FR-3.1-E 보기 필요 단어 수 (정답 1 + 오답 3) |
| `DISTRACTOR_LEVEL_RANGE` | 1 | FR-3.1-E 난이도 ±1 |

**설계 이유**: 규칙 값을 한 곳에 모아 두면 요구사항 변경이 파일 한 곳에서 끝난다. 나중에 값을 조정할 때 로직 코드를 건드리지 않아도 된다.

### 4.2 간격 반복과 상태 (`src/domain/srs.py`)

| 함수 | 입력 | 출력 | 설명 |
|------|------|------|------|
| `next_interval_days(consecutive_correct: int, is_correct: bool) -> int` | 연속 정답, 이번 결과 | 다음 간격(일) | 오답이면 1, 정답이면 `REVIEW_INTERVALS` 조회 |
| `next_consecutive(prev: int, is_correct: bool) -> int` | 이전 연속 정답 | 새 연속 정답 | 정답 +1, 오답 0 |
| `correct_rate(correct: int, wrong: int) -> float \| None` | 정답·오답 수 | 0~100 또는 None | 시도 0이면 None |
| `classify_status(attempts, consecutive, last_result_wrong, next_review, today) -> str` | 진도 값 | 미학습/학습중/복습필요/숙달 | 판정 순서는 프로세스 설계서 P-13 |
| `compute_next_review(today: date, interval_days: int) -> date` | 기준일, 간격 | 복습 예정일 | 단순 덧셈이지만 테스트 기준으로 분리 |

**판정 순서**: `classify_status`는 프로세스 설계서 P-13의 판정 순서를 그대로 구현한다. 기준 값은 4.1의 상수를 쓴다.

### 4.3 퀴즈 구성 (`src/domain/quiz_builder.py`)

**입력 타입**: 후보 단어는 `WordCandidate` (word_id, meaning, level, category, attempts, correct_rate, last_reviewed, next_review, status) 데이터클래스로 받는다. `status`는 `Progress.status`(미학습·학습중·복습필요·숙달)를 그대로 넣으며, 신규·약한 단어 판정에 쓴다. `meaning`은 한글 뜻으로, 뜻 중복 규칙(ADR-08)에 쓴다. DB 모델을 직접 넘기지 않는다.

| 함수 | 역할 |
|------|------|
| `plan_bucket_sizes(total: int) -> BucketPlan` | `wrong = floor(N×0.10)`, `review = floor(N×0.20)`, `new_or_weak = N − wrong − review` |
| `pick_unique_by_meaning(ordered, limit, taken_meanings=frozenset()) -> list[int]` | 앞에서부터 보며 뜻이 겹치지 않는 단어를 `limit`개 고른다 (ADR-08 구현) |
| `select_wrong(candidates, limit, today, taken_meanings=frozenset()) -> list[int]` | 자주 틀린 단어 선정. 기준과 정렬은 P-08 5단계. 뜻 중복 제외 |
| `select_review(candidates, limit, today, taken_meanings=frozenset()) -> list[int]` | 복습 대상 선정. 기준과 정렬은 P-08 5단계. 뜻 중복 제외 |
| `select_new_or_weak(candidates, limit, rng, taken_meanings=frozenset()) -> list[int]` | 신규·약한 단어 선정. 학습 상태가 `미학습`·`학습중`인 단어 (FR-3.1-A, P-08). `rng`로 무작위 순서, 뜻 중복 제외 |
| `fill_shortfall(candidates, excluded_ids, need, rng, taken_meanings=frozenset()) -> list[int]` | 부족분 보충. 기준은 P-08, `rng`로 무작위 선정. 뜻 중복 제외 |
| `build_quiz_plan(candidates, total, today, rng) -> QuizPlan` | 위 함수를 순서대로 호출. 최종 문항 수가 부족하면 `QuizPlan.shortage` 기록. 선정 중 이미 고른 뜻과 같은 뜻의 단어는 건너뛴다 (ADR-08) |
| `split_quiz_types(total: int) -> tuple[int, int]` | `(한→영 개수, 영→한 개수)` = `(floor(N/2), N − floor(N/2))` |

**선정 순서**: 프로세스 설계서 P-08 5단계를 따른다 (FR-3.1-C, D).

**뜻 중복 규칙**: 처리 순서는 P-08, 결정 근거는 ADR-08을 따른다. 이 거르기는 `pick_unique_by_meaning` 헬퍼를 모든 선정 함수가 공유한다.

**재현성**: `rng`를 인자로 받는다 (`random.Random` 인스턴스). 테스트에서 시드를 고정해 결과를 검증한다.

### 4.4 보기 선정 (`src/domain/distractors.py`)

| 함수 | 역할 |
|------|------|
| `pick_distractors(answer: WordCandidate, pool: list[WordCandidate], rng) -> list[str] \| None` | 보기 3개 (한글 뜻 문자열). 후보 부족 시 None |

**보기 선정 규칙**: 3단계 순서와 뜻 중복 제외는 프로세스 설계서 P-08 '보기 채우기'를 따른다 (FR-3.1-E). 세 단계 후에도 3개가 안 되면 None을 반환하고, 호출자(`quiz_service`)가 문항을 제외한다.

### 4.6 DB 모델 (`src/models.py`)

| 클래스 | 테이블 | 관계 |
|--------|--------|------|
| `Word` | Word | `examples`, `progress` (1:1), `quizzes` |
| `Example` | Example | `word` |
| `Progress` | Progress | `word` (UNIQUE word_id) |
| `Quiz` | Quiz | `word` |
| `QuizSession` | QuizSession | 없음 (items_json에 word_id 보관) |
| `Settings` | Settings | 없음 (단일 레코드) |
| `DBVersion` | DBVersion | 없음 (단일 레코드) |

**SQLAlchemy 설정 규칙**:
- `Word.english`: `String(100)`, `unique=True`, 대소문자 무시는 SQLite `COLLATE NOCASE`로 처리
- 모든 `DateTime` 기본값은 로컬 시간 (`datetime.now`), SQLite `CURRENT_TIMESTAMP` 사용 금지
- `Progress.word_id`는 `unique=True`, `Word.progress`는 `uselist=False`
- `ondelete='CASCADE'` 설정 + 연결마다 `PRAGMA foreign_keys = ON`

### 4.7 DB 연결 (`src/database.py`)

| 함수·객체 | 역할 |
|----------|------|
| `create_db_engine(db_path: Path) -> Engine` | SQLite 엔진 생성, connect 이벤트에서 `PRAGMA foreign_keys = ON` |
| `init_engine(db_path)` | 앱 시작 시 한 번 호출, 전역 엔진 설정 |
| `get_engine() -> Engine` | 전역 엔진 조회. `init_engine` 전에 호출하면 오류 |
| `MEMORY_DB = ":memory:"` | 테스트용 인메모리 DB 경로. `StaticPool`로 한 연결을 공유 |
| `session_scope() -> ContextManager[Session]` | 커밋/롤백/닫기를 한 곳에서 처리 |

### 4.11 Service 계층

**`db_init.py`** (FR-1.1)
- `needs_initialization(db_path) -> bool`
- `load_csv_rows(csv_paths) -> list[dict]`: CSV를 읽어 행 목록을 만든다. 빈 분야는 `미분류`, 빈 level은 1로 채운다
- `initialize_database(db_path, csv_paths) -> InitResult`: 처리 순서는 프로세스 설계서 P-01을 따른다 (`load_csv_rows` → `validate_csv_rows`). 검증 실패 시 DB 파일을 만들지 않고 `CsvValidationError`를 던진다. 적재는 한 트랜잭션이며, 적재 중 오류가 나면 DB 파일을 지운다
- `validate_csv_rows(rows) -> list[str]`: 분야 값(일상·비즈니스·미분류), level 범위(1~5), 영어 중복 검사 결과 목록 반환. 빈 목록이면 통과

**`word_service.py`** (FR-1.2~1.4, 1.7)
- `list_words(category, keyword, sort_by, page, page_size) -> WordPage`: 필터·검색·정렬(단어순·상태순·진도순)·페이지. 시도 0인 단어는 모든 정렬에서 맨 뒤. `WordPage`는 items, total_count, page, page_size를 가진다
- `add_word(english, korean, category='미분류', level=1) -> WordInfo` (중복 시 `DuplicateWordError`)
- `update_word(word_id, english, korean, category, level) -> WordInfo` (Progress·Example 유지, 자기 자신은 중복 검사에서 제외)
- `delete_word(word_id) -> None` (CASCADE)
- `find_duplicate(english, exclude_id=None) -> WordInfo | None` (대소문자·앞뒤 공백 무시)

**`example_service.py`** (FR-1.5, 1.6)
- `get_examples(word_id) -> list[Example]`
- `needs_more_examples(word_id) -> bool` (예문이 3개 미만이면 True, 화면에 "직접 추가해 보세요" 안내)
- `add_user_example(word_id, sentence) -> Example` (공백만이면 `ValueError`, 같은 문장이 있으면 추가하지 않음, source='user')
- `delete_user_example(example_id) -> None` (source='user'만 허용)

**`quiz_service.py`** (FR-3.x, 가장 중요)
- `can_start_quiz(category) -> QuizAvailability` (단어 부족·완료 여부 판정)
- `start_session(today) -> QuizSessionView` (재풀이 여부 판정, 구성, `QuizSession` 저장)

- `finish_session() -> SessionSummary` (세션 행 삭제, 결과 요약)
- `stop_session() -> None` (그만하기: 세션 행 삭제, 제출한 Quiz 기록은 유지, 홈으로 이동)
- `save_and_exit() -> None` (앱 종료 시 호출. 진행 중이면 세션 행을 지우지 않고 유지)

**`progress_service.py`** (FR-4.x)

- `category_progress() -> dict[str, CategoryProgress]` (일상·비즈니스·미분류)

**`settings_service.py`** (FR-2.x)
- `get_settings() -> SettingsValue`
- `save_settings(category: str, daily_count: int) -> None` (1~50 검증, category는 선택안함/일상/비즈니스)

**`backup_service.py`** (FR-1.8, 데이터 설계서 5.2)
- `create_manual_backup() -> Path` (`backups/manual_*.db` 생성, SQLite 백업 API 사용. 저장 위치는 고정이며 사용자가 고르지 않음)

## 5. 주요 흐름 (시퀀스)

### 5.1 퀴즈 시작 → 답변 → 완료

```
QuizWidget ─ start() ─→ QuizService.can_start_quiz(category)
                         ├─ 불가 → 안내 대화상자 (단어 부족)
                         └─ 가능
QuizService.start_session(today)
  ├─ 재풀이 여부: Quiz에 is_bonus=0 AND is_retry=0 행이 오늘 있는가
  ├─ WordRepo: 후보 조회 → WordCandidate 리스트
  ├─ domain.quiz_builder.build_quiz_plan(...)
  ├─ domain.distractors.pick_distractors(...) 문항마다 호출
  └─ QuizSession 저장 (items_json) → QuizSessionView 반환

사용자 선택 → QuizService.submit_answer(session_id, index, choice)
  [트랜잭션]
    ├─ Quiz 행 추가 (is_bonus, is_retry 설정)
    ├─ 기본 세션이고 재풀이가 아니면:
    │    progress_service.apply_result() → srs 계산 → status 갱신
    └─ QuizSession.current_index += 1
  [커밋]
  → AnswerResult (정답 여부, 정답 인덱스) → UI 표시

기본 문항 종료 → domain.bonus.select_bonus(...)
  ├─ 빈 리스트 → 결과 화면
  └─ 있음 → 보너스 화면 → start_bonus() → submit_answer (진도 미반영)

finish_session() → QuizSession 삭제 → SessionSummary → 결과 화면
```

### 5.2 단어 추가 → 예문 안내

```

  → WordService.add_word()        (중복 검사 실패 시 중복 대화상자)
```

```
  → ExampleService.add_user_example(word_id, sentence)

```

```
  → QuizWidget.save_if_running()   (세션 행 유지, 현재 위치 저장)

```

```
SettingsWidget [백업에서 복구]
  → 백업 폴더의 파일 선택 → BackupService.validate_backup()
```

## 7. 설계 결정 기록 (ADR)

### ADR-01 GUI 프레임워크: PyQt6
- **배경**: 기획서는 PyQt5 또는 PyQt6로 두었다. 신규 프로젝트이며 학습 대상도 새 세대 API다.
- **대안**: PyQt5 (자료 많음, 구세대), PySide6 (LGPL, 라이선스 유리)
- **결정 근거**: 현행 Qt 6 세대이며 신규 프로젝트에 맞는다. enum 표기가 길어지는 단점은 감수한다. 배포 시 GPL 조건이 문제되면 PySide6로 전환할 수 있도록 UI 코드가 Qt 공통 API 위주로 작성되게 한다.
- **재검토 조건**: 배포 계획이 확정되어 GPL 소스 공개 의무가 부담되는 경우

### ADR-02 예문 출처: 자체 예문 (외부 사전 API 제거)
- **배경**: 처음에는 WordsAPI를 썼다. WordsAPI는 키가 필요해서 학생 각자가 발급하거나 개발자 키를 exe에 넣어야 한다. Free Dictionary API는 키가 없지만 공식 한도가 공개되어 있지 않고, 예문이 없는 단어가 있으며, 서비스가 중단될 수 있다. 한편 CSV에는 1,500단어 모두 예문 3개가 이미 들어 있다.
- **대안**: WordsAPI (키 필요, 배포 부담), Free Dictionary API (키 없음, 예문 누락과 한도 불확실), 개발자 키 포함 배포 (키 노출과 한도 공유), Cambridge (승인 필요)
- **결정 근거**: 학습 단어의 예문은 CSV에 이미 준비되어 있으므로 외부 API가 필요 없다. API를 빼면 키, 네트워크, 한도, 장애 문제가 모두 사라지고 앱은 오프라인으로 동작한다. 예문 품질은 CSV 검수로 관리한다. 신규 단어의 예문은 학생이 직접 입력하며, 3개 미만이면 안내한다 (FR-1.5).
- **재검토 조건**: 학생이 추가하는 단어가 많아 직접 입력 부담이 커지거나, 예문 품질 문제가 반복되어 외부 자료가 필요해질 때. 그때는 외부 연동 인터페이스를 새로 설계한다.

### ADR-03 DB 저장 위치: 배포는 사용자 데이터 폴더, 개발은 프로젝트 data/
- **배경**: PyInstaller `--onefile` 실행 파일은 실행 시 임시 폴더에 풀린다. 그 위치에 쓰면 학습 기록이 사라진다.
- **대안**: exe 옆 폴더 (설치 위치 권한 문제), 프로젝트 data/ 고정 (배포 부적합)
- **결정 근거**: 사용자 데이터 폴더는 쓰기 권한이 보장되고, 재설치해도 기록이 남는다. 개발 모드를 환경 변수로 분리해 개발 중에는 `data/`를 그대로 쓴다.
- **후속 조치**: 배포 빌드 명령에서 `--add-data "data:data"`는 CSV만 넣도록 바꾼다. `.db` 파일은 빌드에 포함되지 않아야 한다 (기획서 10장 수정 필요).

### ADR-04 대상 OS: Windows 우선
- **배경**: 개발 환경이 Windows이고, PyInstaller는 빌드한 OS에서만 실행 파일을 만든다.
- **대안**: 처음부터 Windows·macOS 동시 지원 (Mac 장비 또는 CI 필요)
- **결정 근거**: Windows에서 완성하고 테스트한 뒤 macOS를 추가한다. macOS는 GitHub Actions의 macOS 러너로 빌드하는 방안을 나중에 검토한다.
- **재검토 조건**: Mac 사용자 배포 요청이 생기는 경우

### ADR-05 로그: 필수 포함
- **배경**: DB 오류, 백업 실패, 예문 적재 실패는 사용자 화면만으로 원인을 파악하기 어렵다.
- **대안**: 로그 없음 (요구사항 선택사항), 외부 로깅 서비스
- **결정 근거**: 표준 `logging`으로 구현 부담이 작다. 로컬 파일 로테이션으로 용량 문제도 막는다. 외부 전송은 하지 않는다 (보안 요구사항 3.4).

### ADR-06 접근성 글꼴 조절: 1차 제외
- **배경**: 요구사항에서 선택사항이다. 모든 화면의 레이아웃 검증 비용이 크다.
- **결정 근거**: 1차 목표는 핵심 학습 흐름의 완성이다. 필요해지면 `styles.py`의 폰트 상수를 설정값으로 바꾸는 방식으로 추가한다.

### ADR-07 설계 문서 구조: 계층 분리와 순수 domain
- **배경**: 퀴즈 규칙이 복잡하고, 규칙 변경이 잦을 가능성이 높다.
- **대안**: Service에 로직을 몰아 넣기 (테스트가 DB에 의존함)
- **결정 근거**: domain을 순수 함수로 두면 규칙 테스트가 빠르고 정확하다. 요구사항 변경이 domain 몇 개 파일에 머문다.

### ADR-08 동의어 중복: 한 세션에 같은 뜻 단어는 한 번만 출제
- **배경**: CSV에 한글 뜻이 같은 단어가 160건 있다 (예: `hour`와 `time`이 모두 '시간'). 한→영 문항에서 정답이 두 개가 될 수 있다. 보기 선정은 정답과 같은 뜻을 빼지만, 문항 선정은 같은 뜻을 막지 않았다.
- **대안**: CSV 뜻을 구분해서 고침 (사람이 160건을 검토해야 해서 시간이 많이 든다), 문항 생성 규칙으로 막음, 중복을 허용
- **결정 근거**: 코드 규칙으로 막으면 데이터를 고치지 않아도 되고, 새 단어가 추가되어도 같은 문제가 자동으로 막힌다. 적용 범위는 한 세션(기본 퀴즈 + 보너스)이다. 다른 날에는 같은 뜻의 단어가 다시 나올 수 있어 간격 반복과 충돌하지 않는다.
  - `quiz_builder.build_quiz_plan`: 선정 중 이미 고른 뜻을 가진 단어를 건너뛴다.
  - `bonus.select_bonus`: 기본 퀴즈에 나온 단어와 뜻이 같은 단어를 제외한다.
  - 보기(`distractors`)는 기존처럼 정답과 같은 뜻을 제외한다.
- **재검토 조건**: 뜻 중복 때문에 후보가 부족해지는 경우 (예: 분야 필터 후 단어가 적을 때), 또는 CSV 뜻을 정리하기로 결정한 경우.
